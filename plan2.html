AdaptiShield · Paper 2 proposal

Making AdaptiShield actually adaptive

Paper 1 found that the adaptive layer had nothing to learn from. This plan fixes the signal first, then lets the defense learn while it runs, attacks that learning, and tests everything on data we did not write.

The problem

In paper 1 the adaptive layer did nothing. The learner was not weak. It had nothing to learn from.

  • 0Detector score on address-free attacks, below both detection rules (standalone needs 2, indirect-effect needs at least 1). 23 of 26 recorded address-free cases score (0, 0) while the probe's transcription of the attack is correct.
  • 0Extra attacks caught when the reward is replayed across the whole threshold grid (Phase 6).
  • 24/30Multi-turn turns where the masked and unmasked probes agree, so the drift rule has nothing to add up (Phase 15).

A learner cannot tune a dial connected to nothing. To be adaptive, the system needs a signal that varies with the attack, parameters that change the decision, and feedback that exists outside a benchmark.

Goal: a defense that improves from feedback while it runs, on attacks it was not tuned on, that survives an attacker trying to steer its learning, and that does not raise false positives.

What "adaptive" means here

All four must hold. Pass conditions are pre-registered in Phase 0.

A1 · Phase 4

Changes from feedback

Parameters move during the stream, and every move is logged with its evidence.

A2 · Phase 4

The change helps

Detection after the shift beats the frozen static system; lower 95% bound of the paired gain above 0.

A3 · Phases 4, 5

The change is safe

FPR within the non-inferiority margin, and poisoning attempts are refused.

A4 · Phase 6

It generalizes

The gain holds on the frozen holdout and on a corpus not used in Phases 1–5.

Phase 0

Kaggle setup, freeze, pre-register

Priority 1≈ 1–2 weeks

Set up Kaggle and fix everything that could later be tuned to the answer.

  1. Kaggle setup. Get the API token (the one manual step), extend evaluation/kaggle/ to run the probe with checkpointing, and time 20 probe calls on Kaggle and on the laptop. Rerun the paper 1 static baseline on Kaggle so every comparison shares hardware.
  2. Split InjecAgent. Take the 459 address-free and 51 target-bearing direct-harm cases, exclude the 60 paper 1 already used, and split the rest by fixed seed into dev (≈30%) and frozen holdout (≈70%), stratified by tool family. Commit the index lists before reading any case, then upload them as a versioned Kaggle dataset.
  3. Choose a second benign corpus. AgentDojo's 60 documents are a census and already used. Target at least 300 documents so a small FPR margin is measurable. (to choose)
  4. Power calculation. Fix n and the decision rule for each test. With n = 30 a Wilson interval is about ±20 points; with n ≈ 100 about ±10. (compute exactly)
  5. Pre-registration in evaluation/preregistration/paper2_*.md: hypotheses H1–H6, metrics, n, decision rules, FPR margin, kill tests.
  6. Literature check. Position against masked re-execution (MELON) and task-alignment checking (Task Shield). (to verify)
ExitWorking Kaggle pipeline with timing numbers and the paper 1 baseline rerun there. Splits, pre-registration, benign corpus and positioning notes committed before any Phase 1–2 result exists.
Phase 1

Task-scope scorer

≈ 2–3 weeks · parallel with 2

The probe already describes address-free attacks correctly: "grant permanent access to guest_amy01", "transfer $3,000 to account number 123-1234-1234", "unlock the front door". The scorer only knows data-movement verbs, so it returns 0. The new question is whether the action goes beyond what the user asked for.

  1. Define the check: user task + tool list + proposed action in, scope score out. Graded 0–2 for the existing detector, plus a continuous version for Phase 4.
  2. Implement on gemma3:4b (debug on the laptop, record on Kaggle), comparing the action with the action under the masked input, so it stays a causal check and not a plain classifier.
  3. Measure FPR first, on AgentDojo's 60 benign documents and the new benign corpus, before any attack data.
  4. Run on the dev split only, then freeze the scorer at a commit hash.

Phase 2

Continuous causal score

≈ 2 weeks · parallel with 1

Recorded on Kaggle; gemma3:4b is enough to start. Integer severities round small changes to 0. The scouting run (gemma3:4b, 15 turns) found IE exactly 0 on all 6 benign turns and non-zero on 3 of 9 attacks: too small to conclude, large enough to test properly.

  1. Turn the forced-choice log-probability margin (masked vs unmasked) into a score in [0, 1].
  2. Calibrate on dev data with temperature or isotonic scaling. The scouting margins saturate (12.5 vs 22.6 nats on one turn), so raw margins are not probabilities.
  3. Measure separation on dev: ROC AUC and detection at a fixed FPR.
  4. Re-run the Phase 15 multi-turn sessions to see whether the drift rule can now fire.
  5. Size check: repeat on a 7–8B model on the same Kaggle setup. A 14B model needs 4-bit quantization on a 16 GB P100, and larger, safer models may refuse to state the action. If so, record it as a finding.
ExitA calibrated score with dev AUC clearly above the integer score's. (to measure)
FallbackA calibrated continuous causal score is reusable even without adaptation.
Track 4A

Adaptation harness on Kaggle

Priority 1≈ 2 weeks · parallel with 1 and 2

The learner cannot learn before gate G1, but its machinery can be built and tested now, so Phases 3 and 4 start the day G1 passes.

  1. Build the harness as a Kaggle notebook plus repo module: load saved probe scores, replay an episode stream, apply a parameter set, record decisions, compute metrics.
  2. Implement the weak-label simulator with a noise-rate setting.
  3. Implement the learners behind one interface: grid / coordinate search, Bayesian optimization, contextual bandit.
  4. Implement the safety path: verify on a replay window, gate check that recomputes from raw logs, versioned parameter sets, one-step rollback, drift monitor.
  5. Dry run on paper 1's recorded probe outputs (results/probe_corpus/). The learner should propose no useful change, because the paper 1 signal is flat. Reproducing that no-op is the correctness test.
ExitReproduces paper 1's no-op on old data and runs end to end on Kaggle in one session.

Gate G1 · Is there signal?

Proceed to Phase 3 only if at least one Phase 1 or Phase 2 signal separates attack from benign on dev where the old scorer gave 0. If neither does, skip Phases 3–5 and write Phases 1–2 up as a detection paper.

This is the step paper 1 lacked: never train a learner on a flat signal.

Phase 3

Offline calibration baseline

≈ 1–2 weeks · Kaggle

Before claiming adaptation, show what plain offline tuning achieves. Phase 4 must beat this, not just the static system.

  1. Constrained grid / coordinate search on dev: maximize detection subject to FPR ≤ margin. A constraint, not a weighted reward, because paper 1 showed a reward can pick a rule that scores lower on its own metric (+0.8683 vs +0.8688).
  2. Bayesian optimization with the same constraint, as a second baseline.
  3. Record the oracle-tuned static setting (best fixed parameters in hindsight) for Phase 4.
OutputTwo tuned baselines and an oracle bound, all frozen.
Phase 4

Online adaptation

Core claim≈ 3–4 weeks · Kaggle

Runs in the track 4A harness on saved probe scores. A Kaggle GPU is needed only when a parameter changes the text the model sees (sanitizer settings); keep those to two or three. Adaptation means improving while running as the attack mix changes. This phase makes paper 2 about adaptation rather than tuning.

  1. Build the stream. Order dev episodes with a mid-stream shift: target-bearing attacks first, then mostly address-free, then a new tool family, with benign episodes mixed in at a realistic rate.
  2. Weak labels, which a deployed system actually has:
    • egress block (Layer 4) on an action the detector allowed → likely missed attack
    • user rejects or undoes an action → likely missed attack
    • user overrides a block → likely false alarm
    • masked and unmasked probes disagree strongly → likely attack
    Simulated from ground truth with a stated noise rate, reported at several noise levels.
  3. Learner: a contextual bandit per tool family over the Phase 3 parameters, with an FPR constraint.
  4. Safety path: propose → verify on a replay window (CI-aware) → Layer 5 gate recomputes from raw logs and checks outside benign data → version in git → one-step rollback. Paper 1's learned gain produced 36 false positives of 68 on external data while every internal check passed.
  5. Drift monitor: if rolling FPR or detection leaves its band, freeze learning and alert.
MetricsCumulative detection and FPR; detection after the shift; episodes to recover; regret vs oracle; refused updates.
Compared againstStatic AdaptiShield, Phase 3 offline tuning, oracle-tuned static, random search.
Exit · A1, A2Online beats static and offline-tuned after the shift; paired gain lower bound above 0.
FallbackIf online only matches offline, the verified-update pipeline plus the new signals are still the contribution.
Phase 5

Feedback poisoning

≈ 2 weeks · Kaggle

Any defense that learns from feedback can be steered by whoever controls part of that feedback. A security reviewer asks this first.

Threat model: the attacker can place documents in the stream and cause some weak labels (for example benign-looking episodes that trigger user overrides). The attacker cannot change the gate or the code.

  1. Loosening attack: benign-looking episodes that push task-scope strictness or thresholds down, followed by address-free attacks.
  2. Tightening attack: induce false-alarm labels until the system blocks legitimate work.
  3. Count the poisoned episodes needed to move a parameter, with and without the verify step and the gate.
MetricsAttack success after poisoning; episodes needed; share of poisoned updates refused by verify vs by the gate.
Exit · A3With the gate on, poisoning cannot raise attack success above the static system's. (target)
Why it helpsIt turns paper 1's human gate from a precaution into a measured defense against learning attacks.

Summary

Paper 1: causal detection works when the attack names something an action can copy (93.3% on InjecAgent) and hardly at all when it does not (10.0%). The adaptive layer was inert because its signal was flat.

Paper 2 sets up Kaggle as the single run platform and builds the adaptation harness there first, freezes the data, fixes the signal with a task-scope scorer and a calibrated continuous score, tunes offline as a baseline, adapts online on a shifting stream behind a verify step and a human gate, attacks the learner through its own feedback, and proves it on a frozen holdout and data we did not write.

Causal detection can be extended beyond targets an action can name, and it can adapt online to a changing attack mix without raising false positives, under a gate that resists feedback poisoning.

This is the claim if the plan works. Nothing in it has been measured yet.
